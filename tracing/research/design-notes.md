# tracing — Design Notes

> 2026-04-22. Author: Claude Sonnet 4.6 (design-phase analysis).

---

## Load-bearing decisions

**The ProbeAction enum is the most important design decision in this spec, and it is underspecified.** §3.2 defines `ProbeAction` as a fixed enum — deliberately not a VM. This is the right call: no eBPF-style untrusted code in probe handlers. But the proposed variants (`Capture`, `IncrementCounter`, `FnTime`, `Snapshot`, `RecordTo`) are not closed under composition in a useful way. A real tracing session needs "capture fields from this function, increment a counter if field X > threshold, and snapshot the scheduler ring if field Y == domain N." The `Chain` variant is mentioned parenthetically but not defined in the enum. Before Stage 3, the composition story must be finalized. If `Chain` is unbounded, it is isomorphic to a program; if bounded to depth 2 or 3, it is probably sufficient.

**The per-CPU shadow stack for FnTime is a memory hazard in domain-switch-heavy workloads.** §3.2.1 says "a per-CPU shadow stack (in the tracer's domain) tracks nested calls." Domain-switching frequently resets the notion of "current domain" but not "current CPU." If code in domain A calls code in domain B (via a domain-entry path, not via IPC), and both A and B have FnTime probes, the shadow stack in the tracer domain must be accessible from both domain contexts. This requires either that the tracer domain is always readable from any executing domain (weakening isolation) or that the shadow stack is in a shared-memory region between the producer domain and the tracer domain (requiring a shared cap, per-domain shadow stack per caller domain, or some other design). The spec does not resolve this.

**Flight-recorder `record` at ≤20 cycles is a hard real-time claim that conflicts with the overwrite-oldest semantics.** The slot-claim via `fetch_add` is lock-free and bounded. But "overwrite oldest" requires a sequence number per slot, and the producer must write payload after the slot claim — two stores separated by arbitrary payload copying. If the payload is large (e.g., a struct with 8 fields), the write window is not zero. During that window, a concurrent reader taking a snapshot will observe a partially-written slot. The spec says "release store of a per-slot `seq`" which implies the snapshot reader waits for the seq before reading, but this means the snapshot code must do a spin-wait on each slot's seq — the snapshot is not bounded to ≤50 µs for a 64 KiB ring if producers are slow-writing. This is the classic Disruptor problem; the spec should reference the Disruptor pattern explicitly and decide on single-writer vs. multi-writer semantics.

**The tracer task lives in a reserved domain, but it consumes from all other domains' rings.** §3.4 says "the tracer can never see domain D's events without an explicit cap grant." But the *tracer task's data structures* (its own aggregates, forwarding state) live in the tracer domain. For the tracer to receive events from domain D, it must either (a) have `Cap<TraceRing<D>, Recv>` and do a ring pop (which requires entering domain D momentarily to read the ring, or the ring must be shared-readable), or (b) domain D's ring is mapped shared into the tracer's address range with the tracer's read right. Option (b) is the only one that avoids a domain-switch per event, but it means the tracer domain's address space has read-mappings into every other domain. A compromised tracer can then read *all* kernel domains, which is the exact opposite of the isolation the spec promises.

**tDigest vs HdrHistogram is deferred but has real memory consequences.** §3.5 notes tDigest is chosen "for unknown-range metrics." The tDigest paper (Dunning & Ertl, 2019) documents that at compression factor 100, a tDigest uses ~7,200 bytes. For an HdrHistogram covering 1 ns to 1 s at 3 significant figures, memory is ~30 KiB but queries are O(1). Per-probe aggregate storage on the hot path (producer-local) adds 7 KiB per FnTime probe. On a system with 200 probed functions, that is 1.4 MB of sketch data in producer domains. This is not a blocker, but it must be a known line item in the memory budget.

## Divergences from precedent

**DTrace's speculative tracing vs. NARF's flight-recorder:** DTrace's `speculate()` / `commit()` / `discard()` keeps a private event stream until commit. NARF's flight-recorder is overwrite-oldest — it does not have a speculate/discard mechanism. This means that NARF's flight-recorder cannot implement "record everything, but only keep it if the operation fails." The panic-snapshot model (freeze on panic) is a weaker version of DTrace speculation. For the scheduler recorder (capture every context switch, snapshot on assertion fail), this is adequate. For IPC recorders (capture every message, snapshot only on corruption), the lack of discard means normal-path events consume ring space continuously — the ring must be large enough that by the time a corruption is detected, the relevant prior events are still in the ring. This is a ring-sizing question that needs explicit guidance.

**Linux ftrace's function_graph vs. NARF's FnTime:** Linux's function_graph tracer uses a `-pg` mcount preamble in every function, giving zero per-function setup cost (all functions are pre-instrumented). NARF's FnTime requires installing probes at specific addresses — it is more like BPF function entry probes than ftrace. The overhead target of ≤200 cycles for FnTime with 0 HW counters is achievable only if the probe handler is inlined near the probe site (via a trampoline allocated in the domain's code area). The trampoline allocation at probe install time is not mentioned in §3.2.1 but is implied by the aarch64 note about out-of-range veneer allocation. This must be part of the probe install path.

**KProbes optimized path vs. NARF's single-byte arming:** Linux's optimized kprobes use a 5-byte jump when the call sequence fits (x86_64), avoiding the int3 breakpoint overhead. NARF's spec mentions "int3 synchronisation sequence per Intel SDM Vol. 3 §8.1.3" which is correct but incurs the full 3-step stop/patch/resume cycle. For Stage 3 where a small number of probes are installed interactively, this is acceptable. For Stage 4 where userspace tooling may install/remove many probes rapidly, the batched arming described in the research notes ("arm N probes in one stop-the-world pass") is essential and should be specified, not just mentioned in research notes.

**Java Flight Recorder's chunk model:** JFR writes events in chunks with constant-pool tables for frequently repeated data. NARF's flight-recorder has no chunk or table concept — events are raw structs. For high-cardinality fields (call stacks, file paths, task names), raw struct recording wastes ring space. Consider adding a `StringIntern` side-table per recorder that maps repeated strings to 16-bit IDs, reducing per-event size for the scheduler and IPC recorders.

## Proposed spec changes

- **§3.2 Dynamic probes — define `ProbeAction::Chain` formally:** Specify: `Chain(&'static [ProbeAction])` with a maximum depth of 8, no cycles, no allocations in chain evaluation. Document that the total action chain cost must be estimated at install time; if the estimated cost exceeds the probe's declared budget, `install_probe` returns `Err(BudgetExceeded)`.

- **§3.2.1 FnTime — resolve the shadow-stack domain-access problem:** Add a design note: "The per-CPU shadow stack is a memory region tagged with the TRACER domain key but also read/write accessible from any domain that holds a `Cap<FnTimeShadow<D>, RW>` cap. The Frame grants this cap to each domain at boot time. This grants the tracer read/write into the shadow stack, but domain D code can only write to the shadow-stack slots designated for domain D by the cap's range constraint." This must be co-designed with `memory/` §4.

- **§3.3 Flight-recorder — specify snapshot consistency model for partial writes:** Add: "During snapshot, a slot whose seq field does not match the expected sequence number (indicating a write in progress) is copied optimistically and marked `Partial` in the snapshot output. The snapshot never spins. Consumers of the snapshot must tolerate `Partial` slots." This bounds snapshot latency unconditionally.

- **§3.4 Trace transport — document the tracer's read access model:** Specify whether the tracer domain has read-only mapped views of each producer domain's trace ring (zero-copy read) or whether producers push into a shared-neutral ring. The security implications of each must be stated: shared-neutral is safer; mapped-view is lower latency.

- **§7 Stage assignment — add Stage 1 ring sizing guidance:** "Stage 1 flight-recorder rings are fixed size (configurable at compile time, default 4 KiB per ring). The default ring count and size must be documented in a `tracing/config.md` alongside the ring structure layout."

- **§8 Open questions — add ring-size policy guidance for DTrace-style discard:** "Recorders used for 'record-unless-error' semantics (IPC corruption detector, capability violation recorder) need ring sizes large enough to retain at least N seconds of history under peak load. Define a ring-sizing formula: `ring_slots ≥ max_event_rate_per_sec × target_retention_sec`, documented per-recorder."

## Open invariants / cross-subsystem hazards

**`frame/` §? (panic path → snapshot invocation):** §3.3 says the panic path calls `tracing::snapshot_panic_rings()`. But `frame/`'s panic path is the most constrained execution context in the kernel: no allocation, no scheduler, possibly no working stack if the panic was a stack overflow. `snapshot_panic_rings()` must be callable from this context — it must use pre-allocated buffers only, no recursive locking, and bounded time. The spec says this is so, but `frame/` does not have a corresponding invariant that its panic path can invoke this function safely. Add a cross-reference: `frame/` §4 must state "panic path may call into `tracing/` snapshot; `tracing/` guarantees no allocation, no scheduler, and bounded execution time in this path."

**`memory/` §4 (domain for the tracer):** The spec says the tracer lives in `DomainId::TRACER` reserved by `memory/`. But `tracing/` §3.4 also says each producer domain has a streaming ring, and the tracer holds `Cap<TraceRing<D>, Recv>` for each. Who allocates these per-domain rings? If `memory/` allocates them tagged to the producer domain, then the tracer needs read-access to those pages. If they are allocated in the tracer domain, producers need write-access. Neither option is pure from an isolation perspective. This needs a joint design decision at `memory/` §3 and `tracing/` §3.4.

**`capabilities/` §? (probe install cap vs. TCB probing):** §4 says "a probe on a TCB function requires a TCB-scoped install cap." The `Cap<Probe, Install>` type must therefore carry a scope (TCB vs. non-TCB). This scoping is not described in the current public interface. If `capabilities/` does not define scoped install caps, probing TCB code requires a separate cap type (`Cap<TcbProbe, Install>`), which must be minted under the TCB change-class process rules from `process/`.

**`rcu/` §? (probe metadata reclamation):** §6 says `rcu/` Epoch reclamation is used for probe-site metadata on arm/disarm. The metadata (trampoline, arg map, action chain) must not be freed while any CPU is in the middle of executing the probe. RCU provides this guarantee only if probe handlers complete within a grace period. If a probe action includes `FnTime` with streaming (`stream: true`), the probe remains "executing" for the duration of the stream ring push. The RCU grace period logic must be extended to cover the full action chain, not just the instruction-fetch window.

## Additional opinionated commentary

The tracing spec is the most fully worked-out of the eight subsystems — it has overhead targets, composition rules, and multiple concrete use cases. The biggest gap is the security model for the tracer-domain isolation inversion problem: a privileged tracer that can read all domains is not more secure than a monolithic kernel — it just moves the privileged component from the TCB to the tracer. The solution (scoped `Cap<TraceRing<D>, Recv>` per domain, tracer can only see what it is explicitly granted) is stated correctly, but the implementation path (tracer reads ring D → must map or enter domain D momentarily) creates a window. The safe implementation is a push model: each producer domain's ring-flush task runs in domain D and pushes into a neutral shared ring that the tracer reads. This is messier than the pull model but avoids any tracer→domain memory access. The spec should decide and document this explicitly, as it affects the entire tracing architecture from Stage 2 onward.

The FnTime overhead targets (≤200 cycles, ≤600 cycles with 4 HW counters) are ambitious but achievable. The key risk is the PMU context-switch interaction: reading four hardware counters with `RDPMC` takes about 30–40 cycles each, plus RDTSC adds 25–40 cycles, totaling ~170 cycles for 4 counters + time — just under the ≤600 cycle budget. But `RDPMC` requires that the counter was enabled by the kernel (`CR4.PCE` or `RDPMC` privilege), and multiplexing (more counters requested than hardware provides) breaks the per-call delta model entirely. The spec must state that FnTime with N > `hw_counter_count` is a hard install-time error, not a degraded-accuracy mode.
