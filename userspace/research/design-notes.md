## Load-bearing decisions

**Spawn-only (no fork) is the right call, but the spec does not fully reckon with the relibc consequence.** relibc targets Redox, which also has a spawn-only model. However, relibc's `posix_spawn` implementation goes through a `vfork`-then-`exec` path on Linux-hosted builds, and several relibc functions (`popen`, `system`, `pthread_atfork`) assume fork is available. NARF must audit relibc for fork-path invocations and either stub them out or implement safe alternatives. The §8 open question "how far can we get with spawn-only before POSIX compat breaks?" is not rhetorical — the answer from Redox's experience is "far enough for most server applications, but not for applications that shell out." This should be a hard decision in §8, not a deferred question.

**The two-ring-pair bootstrap (submit + complete) is underspecified for multiple concurrent services.** §3 says "every new process receives two ring pairs (submit + complete)." But a process that needs to talk to both the filesystem and the network stack requires ring pairs to each. The initial two ring pairs are presumably for the kernel ABI itself. Application-level IPC to multiple services requires additional ring pairs, which must be granted via `capabilities/`. The bootstrap config page describes "capability handles to parent-granted services," but the number of initial ring pairs and the mechanism for acquiring more are not specified. This must be resolved before Stage 4 begins.

**The `PT_INTERP`-as-bootstrap-site (Shiva-inspired) is in §8 as an open question but should be a decision.** The NARF program interpreter must: (1) set up the submission/completion Narf-Rings, (2) install the per-task cap table, (3) initialize TLS, (4) resolve relocations. This is exactly what a custom `PT_INTERP` binary does. The alternative is a vDSO-like mechanism that runs before `_start` via a special ELF section. The `PT_INTERP` approach is cleaner and matches existing tooling (glibc's `ld.so`, musl's linker, Shiva) but requires maintaining a separate interpreter binary. The vDSO approach is simpler to deploy but harder to compose with dynamic linking. Given that NARF starts static-only (§8 open question "dynamic linking: do we ship `ld-musl`-style dynamic linker, or static-only first?"), the vDSO bootstrap page in §3 is probably sufficient for Stage 4. The Shiva/`PT_INTERP` path is the right architecture for Stage 5+ dynamic linking.

**User PKU (Ring 3 side) is described as independent from kernel PKS (Ring 0 side) except where explicitly shared.** §4 says this correctly. But the 16-domain ceiling means the kernel may have used most of the PKS keys for its own drivers by the time a user process needs user-mode domain isolation. On current x86_64, PKU and PKS share the same 16-key namespace but apply to different privilege levels — a user process with PKU key 3 and the kernel's driver domain with PKS key 3 are entirely separate; they do not conflict. The spec's statement is correct but potentially confusing: clarify that PKU keys in user processes are a fully separate namespace from PKS keys in the kernel.

**Signals are unaddressed but cannot be deferred past Stage 4.** The §8 open question is "do we support them at all, or use cap-based equivalents?" Signals are the primary mechanism for asynchronous process notification in POSIX — they are used for SIGCHLD (process exit notification), SIGTERM (graceful shutdown), SIGPIPE (broken pipe), and SIGSEGV (memory fault). `relibc` implements all of these. If NARF does not support signals, relibc's signal-handling code must be stubbed, which will silently break applications that register signal handlers. The minimum viable signal support for Stage 4 is: SIGTERM, SIGCHLD, SIGPIPE as capability-delivered async notifications; SIGSEGV/SIGBUS as synchronous fault delivery. A full POSIX signal mask is a Stage 5+ item.

## Divergences from precedent

**Fuchsia starnix vs. NARF's native-first model:** Fuchsia's starnix runs a Linux-compatible kernel as a Fuchsia component, translating Linux syscalls to Fuchsia APIs. NARF takes the opposite approach: native-first NARF ABI with relibc as a thin compat layer. The starnix approach offers broader compatibility immediately but adds a translation layer that is both complex and performance-penalizing. The NARF-native approach requires relibc to be ported to the NARF ABI, which is a real engineering cost, but it keeps the kernel clean and avoids the combinatorial explosion of "every Linux syscall variant must be handled." The NARF-native path is correct architecturally; the implementation risk is that relibc's port to a non-Redox system has not been tested outside Redox's model.

**seL4's process model vs. NARF's:** seL4 has no process abstraction at the kernel level — tasks are just TCBs, and a "process" is a userspace-level convention managed by a root task. NARF's §3 defines `Process { cap table root, VM root, threads }` as a first-class kernel type. This is closer to Fuchsia's "job/process/thread" hierarchy than seL4. The benefit is that the kernel can enforce process-level invariants (e.g., a process's cap table is not accessible without `Cap<Process, Own>`). The cost is that the kernel has a larger TCB surface — `spawn_process` and `exec_into` are TCB operations that must be reviewed to the TCB standard. The spec should explicitly place the ELF loader in the TCB or out of it. If the ELF loader is in-kernel and TCB, every ELF parsing bug is a TCB-class security issue. If it is outside the TCB (e.g., in a separate loader domain), the kernel only needs to validate the capability bundle passed to `spawn_process`, not the ELF content.

**Redox relibc experience:** Redox's relibc is the closest implementation precedent. Redox's syscall ABI is synchronous IPC (Redox uses a blocking `syscall!` macro). NARF's ABI is async (submission/completion rings). relibc will need non-trivial modifications to submit operations to a ring rather than making blocking calls. Every function in relibc that currently calls a kernel syscall must be rewritten to: (a) push a descriptor to the submission ring, (b) wait for the completion ring entry, (c) return the result. In a single-threaded program, "wait" is a busy-poll or a `yield`. In a multi-threaded program, "wait" requires futex-equivalent synchronization. This is the most significant implementation challenge in Stage 4, and the spec does not acknowledge it.

**musl vs. relibc for POSIX surface area:** musl is more complete than relibc (full C99/C11/POSIX.1-2017). For Stage 4, relibc is the stated choice because it already targets a non-Linux kernel (Redox). musl would require more porting work but would give broader application compatibility. The trade-off should be documented explicitly: relibc saves porting time now at the cost of reduced POSIX coverage; musl is broader but harder to port. A future "POSIX mode" using musl is worth planning.

## Proposed spec changes

- **§3 Public interface — specify ring-pair allocation for multi-service processes:** "A new process receives an initial two ring pairs for the kernel ABI. Additional ring pairs for service communication are acquired by presenting `Cap<RingPair, Alloc>` to the kernel's ring-pair allocator. The bootstrap config page includes `Cap<RingPair, Alloc>` as a pre-granted capability. Maximum ring pairs per process is a system-wide tunable with a documented default (proposed: 64)."

- **§4 Invariants — clarify PKU/PKS namespace independence:** Replace "User PKU matches kernel PKS domain IDs only where explicitly shared; otherwise they are independent namespaces" with: "PKU keys (Ring 3 access control) and PKS keys (Ring 0 access control) occupy the same numeric space (0–15) but are entirely independent hardware mechanisms. A user process with PKU key 3 and a kernel driver domain with PKS key 3 do not interact. No sharing of these namespaces is possible; the `explicitly shared` clause refers to shared memory regions that are mapped with both a user-accessible PKU key and a kernel-accessible PKS key."

- **§8 Open questions — decide signal minimum viable surface for Stage 4:** Promote to a design decision: "NARF Stage 4 delivers synchronous fault-signals (SIGSEGV, SIGBUS, SIGFPE, SIGILL) as cap-delivered fault events. SIGTERM and SIGCHLD are delivered as capability-mediated async notifications. Full signal mask, SA_RESTART, and real-time signals are post-1.0. relibc's signal handling is stubbed for unsupported signals with `ENOSYS` on `sigaction` for those signal numbers."

- **§8 Open questions — decide on ELF loader trust boundary:** "The ELF loader (`elf/` module) is placed in the TCB if and only if it is called from the kernel's `spawn_process` path. To minimize TCB surface, the ELF loader runs as a separate task in a dedicated `loader` domain (not DomainId::FRAME). The kernel's `spawn_process` only validates that the `elf: &Elf` reference was parsed by a trusted `Cap<Loader, Parse>` holder. This reduces the TCB blast radius of ELF parsing bugs."

- **§2 Assumptions — add relibc async-ABI porting note:** "relibc's syscall layer must be rewritten for NARF's submission/completion ring ABI. The porting strategy is: each relibc syscall wrapper submits to the ring and calls `ring_wait(token)` which spins or yields until the completion entry arrives. Multi-threaded relibc uses `lib/`'s async `Mutex` on the ring submit slot. This porting work is a Stage 4 pre-requisite item."

- **§7 Stage assignment — add loader domain assignment:** "The ELF loader domain (`DomainId::LOADER`) is allocated at Stage 4 entry. Document that this consumes one of the 16 PKS/MTE domain slots. If domain budget is exhausted (see `memory/` §8 multiplexing question), the loader domain shares with another low-privilege domain — decision deferred to `security-model/`."

## Open invariants / cross-subsystem hazards

**`abi/` §? (async submission/completion ring ABI) ↔ `userspace/` §3 (process bootstrap):** The `abi/` spec owns the stable kernel-userspace boundary. `userspace/` §3 says processes receive "two ring pairs (submit + complete)" and "a read-only config page with capability handles." The exact format of the config page, the ring descriptor layout, and the bootstrap sequence (does the interpreter receive control before or after the ring pairs are mapped?) must be co-designed by `abi/` and `userspace/`. Currently neither spec owns the bootstrap page format. Assign ownership to `abi/` (it is part of the ABI boundary) and add it to `abi/` §3.

**`capabilities/` §? (per-task cap table) ↔ `userspace/` §2 (assumptions):** §2 says "`capabilities/` mints per-task cap tables." But who determines the initial capability set? At spawn, the parent passes a `CapBundle`. The kernel must validate that every cap in the `CapBundle` is a cap the parent itself holds — it cannot grant caps it does not have. This is the standard capability transfer invariant (seL4: you can only delegate rights you hold). It must be in both `capabilities/` §4 and `userspace/` §4 as an explicit invariant.

**`filesystem/` §? (per-task root caps) ↔ `userspace/` §6 (dependencies):** §6 lists `filesystem/` as providing per-task root caps. But `filesystem/` lands in Stage 3 and `userspace/` in Stage 4. The Stage 4 process model requires a filesystem root cap at spawn time. If `filesystem/` is not fully functional at Stage 4 entry, processes cannot be spawned with a filesystem root. Stage 3 must deliver a minimal filesystem root cap (even if it only covers initramfs) that `userspace/` can use in Stage 4.

**`net/` §3.5 (stack daemon attach) ↔ `userspace/` §3 (process model):** The stack daemon is a userspace process that uses `Cap<Stack, Install>`. This means `userspace/` must be functional before the stack daemon can attach, and `net/` Stage 4 items depend on `userspace/` Stage 4 items. More subtly: the stack daemon must be able to register Narf-Ring connections from other user processes (the socket API). This requires `userspace/`'s inter-process IPC ring-pair allocation to be stable before the stack daemon API is locked. These should be co-designed.

## Additional opinionated commentary

The ELF loader placement decision is the most consequential open question in this spec. A bug in the ELF loader is historically the source of a significant fraction of OS privilege escalation vulnerabilities. On Linux, the ELF loader (`fs/binfmt_elf.c`) has had CVEs regularly. NARF must not put ELF parsing in the TCB unless there is a compelling reason. The `Cap<Loader, Parse>` approach — where a separate loader domain does the parsing and presents a validated result to the kernel — is the right architecture. The cost is one more IPC round-trip at process creation time, which is negligible (process creation is not a hot path).

The relibc async-ABI rewrite is the hardest single engineering task in Stage 4. Every function in relibc that wraps a syscall — `open`, `read`, `write`, `close`, `connect`, `accept`, `mmap`, `munmap`, `futex`, and 200+ others — needs its inner loop rewritten from a synchronous `syscall!()` to an async ring submission + wait. This is not a weekend project; it is a multi-month effort. NARF should plan for it explicitly: hire or designate a contributor to own the relibc port before Stage 4 begins, and measure progress by function completion (e.g., `open`/`read`/`write`/`close` in Stage 4 v1 is sufficient for a "hello world" static binary, which is the Stage 4 exit criterion). Trying to port all of relibc simultaneously will cause Stage 4 to slip indefinitely.
