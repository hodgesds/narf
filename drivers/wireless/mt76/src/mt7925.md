# mt76 MT7925 (CONNAC3) — Wi-Fi 7 2x2

> Status: fixture-validated, **not hardware-proven**. Every claim in this
> document is grounded on NARF tip `e883edc3f` (merge #2506) and upstream
> torvalds/linux master `4dce97c6c26` (verified 2026-11-25). The four open
> hardware gates in §8 are the difference between "the fixtures pass" and
> "the card works" — do not read this document as a claim that the MT7925
> has run on real hardware. It has not.

This is the CONNAC3 companion to the CONNAC2 specification
[`../specification/mt7921.md`](../specification/mt7921.md) (3498 lines,
`# mt76 MT7921/MT7922 — Specification`). That spec is deliberately **not**
widened to cover MT7925: its §3 (lines 115–141) already records the UNI /
FWDL / DMA basics and its EHT section (§1771+) the negotiated EHT profile,
and this document fills the gaps rather than duplicating either. Where the
two overlap, the spec is the authority and this document points at it.

Tracker: #2494 (MT7925 programme). Programme record:
`~/workspace/queue/mt7925-program-2026-11-24.md`.

## 1. Identity: what the MT7925 is

- MediaTek MT7925, Wi-Fi 7 2x2, CONNAC3. The card on Daniel's Alder Lake
  machine is PCI `14c3:0717` at `57:00.0`; the canonical PCI id is
  `0x7925` and `0x0717` is its alternate SKU.
- PCI ids, `drivers/wireless/mt76/src/mt7921/regs.rs`:
  `MTK_DEV_MT7925 = 0x7925` (:54), `MTK_DEV_MT7925_ALT = 0x0717` (:58),
  both in `ALL_DEV_IDS`; `is_mt7925_did` (:77) is the predicate every
  per-chip branch keys off — the DMA layout and the register map select
  on the PCI id, **not** on the raw `MT_HW_CHIPID` value, because the
  chip-id gate is still closed (see §8, Q1).
- Upstream has no `0x7925` chip-id constant: `mt7925.h` only defines
  `MT_EE_CHIP_ID = 0x000`, an EEPROM offset. The only place upstream
  switches on `0x7925` is the firmware-selection `case 0x7925` in
  `mt792x.h:562,582`. NARF mirrors that: the PCI id is the identity the
  driver trusts today; the chip-id read is an open gate, not a constant.
- The MT7925 code lives in two places, and the split is deliberate:
  `src/mt7925/` (`mod.rs`, `mcu.rs`) holds only what is CONNAC3-specific
  — the UNI MCU framing, per-link BSS info, EHT MLD TLVs and per-link
  station add/assoc/remove builders. Everything shared with CONNAC2
  (PCI probe, BAR/L1 windows, WFDMA scaffolding, firmware transport)
  stays in `src/mt7921/` and is keyed off `is_mt7925_did`.

## 2. CONNAC3 register map

- Fixed windows: `FIXED_MT7925` in
  `src/mt7921/registers.rs:97–149` — **51 windows**, verified
  entry-for-entry against upstream `mt7925/pci.c:178`
  (`default_fixed_map`), which is the same 51 real windows plus a
  `{0,0,0}` terminator. (CONNAC2 `FIXED` is 44 windows; the CONNAC3
  table is a different table, not an extension.)
- Two entries that have bitten before, pinned by the golden test in
  `registers_tests.rs:286–346`:
  - `(0x7c500000, 0x060000, 0x200000)` — the remap length is `0x200000`
    (2 MiB), **not** `0x2000000`.
  - `(0x70020000, 0x1f0000, 0x0010000)` — reserved for CBTOP, cannot
    switch windows.
- Address translation: `registers::plan` maps a chip address to a BAR0
  offset, selecting `FIXED_MT7925` when `is_mt7925(did)` (:155) and the
  CONNAC2 table otherwise. A fixed window owns its tail word: an access
  at exactly `delta == size` is `Err(Unsupported)` before the L1
  fallback runs, grounded in upstream `__mt7925_reg_addr`
  (`ofs > size` skips). (This was #2501: the `0x74031000` tail-word
  miss that hit the L1 range instead of the fixed table.)
- Identity registers (`regs.rs:84–90`, per Linux `mt792x_regs.h`):
  `MT_HW_CHIPID = 0x70010200`, `MT_HW_REV = 0x70010204`,
  `MT_HW_BOUND = 0x70010020`. What `MT_HW_CHIPID` returns on a real
  7925 card is Q1 (§8) — the driver must not assume `0x7925`.

## 3. Firmware catalog

The MT7925 blob pair, `src/mt7921/regs.rs:231–236`:

| Blob | Name |
|---|---|
| ROM patch | `mediatek/mt7925/WIFI_MT7925_PATCH_MCU_1_1_hdr.bin` (`MT7925_ROM_PATCH`) |
| Runtime ("WM") firmware | `mediatek/mt7925/WIFI_RAM_CODE_MT7925_1_1.bin` (`MT7925_FIRMWARE_WM`) |

- Upstream: `mt792x.h:51` (`MT7925_FIRMWARE_WM`) and `:59`
  (`MT7925_ROM_PATCH`). Also recorded in
  `verification/data/wifi-firmware/profiles.json` and in the spec
  (`mt7921.md:205–206`).
- Resolution: `firmware_blobs_for` maps both 7925 DIDs (`0x7925`,
  `0x0717`) to this pair (`pci_common.rs:130`), and `Firmware::open` hands the
  pair to the same chip-agnostic `Firmware::prepare` used for CONNAC2.
  `prepare` does not gate on the trailer `chip_id` byte, so a 7925
  trailer is accepted exactly like a 7922 one — which is why the `0x25`
  trailer byte is a convention, not a verified fact (see §8).
- Staging is Q2 (§8): the blobs come from Daniel's CachyOS tree. Until
  they are staged, no firmware download can run against the real card,
  and every FWDL claim in this document is fixture-level.

## 4. UNI layer

CONNAC3 speaks the unified (UNI) MCU command set instead of the CONNAC2
ext-cmd framing (Linux `mt7925/mcu.c`; NARF `src/mt7925/mcu.rs`). The
spec §3 (lines 115–141) already records the shape; this section pins the
NARF side of it.

- Command words: `MCU_UNI_CMD` / `MCU_WM_UNI_CMD` /
  `MCU_WM_UNI_CMD_QUERY`, plus the `mt7925_mcu_rxd` event header
  (`mcu.rs`). Station add/assoc/remove are
  `MCU_UNI_CMD(STA_REC_UPDATE)` messages built per link.
- TLV order: station update is `sta_req_hdr` + BASIC + `cap_tlvs` +
  STATE (+ MLD + EHT MLD when `mld` is set and the state is not NONE),
  built by `build_uni_sta_update_req`; one message per active link,
  primary first. BSS info is `MCU_UNI_CMD(BSS_INFO_UPDATE)` in the
  fixed order BASIC, SEC, RATE, QoS, MLD, IFS, then HE + BSS_COLOR when
  the BSS supports HE, then RLM + MBSSID when enabling; the BSS EHT TLV
  travels as its own standalone `BSS_INFO_UPDATE`
  (`mt7925_mcu_set_eht_pp`). The CONNAC2 WTBL nested TLVs of
  `peer_record_on` have no UNI-station-update counterpart — WTBL
  programming on 7925 is a separate WTBL-update path.
- Teardown: remove is `STA_REC_REMOVE` + a bare `STA_REC_MLD_OFF` TLV
  (tag + length only, 4 bytes; `STA_REC_MLD_OFF = 0x23`, `mcu.rs:268`,
  emitted at :754).
- EFUSE goes over UNI `EFUSE_CTRL` (`UNI_CMD_EFUSE_CTRL = 0x2d`,
  `mcu.rs:108`): `MCU_UNI_CMD(EFUSE_CTRL)` to set buffer mode
  (`mt7925_mcu_set_eeprom`), `MCU_WM_UNI_CMD_QUERY(EFUSE_CTRL)` to read
  16-byte blocks (`mt7925_mcu_read_eeprom`) — **not** the CONNAC2
  `MCU_EXT_CMD_EFUSE_ACCESS` that `mt7921::mcu` cites.
- Transport: UNI commands travel on TX MCU_WM (queue 15,
  `regs::MT7925_TXQ_MCU_WM`) with responses on RX MCU_WM (queue 0).
  No live UNI send path exists yet — the builders are byte encoders
  with golden smokes under the existing `drivers/wireless/mt7921` test
  tag, and the live send path will use the DMA `RingMap` (§5).
- MAC init is per-chip where it has to be: MT7925's MDP base is
  `0x820cc800` (`mt7925/regs.h`) versus `0x820cd000` on CONNAC2, and the
  7925 DCR0 write sets DAMSDU_EN only (`mt7925_mac_init`); the per-band
  LMAC writes are shared (`mt792x_mac_init_band`).

## 5. DMA

- Layout: 5-ring, `mt7925_dma_layout` in `src/mt7921/dma.rs` (order per
  upstream `mt7925/pci.c:710-742`). Queue ids follow Linux
  `enum mt7925_txq_id` (`mt7925.h:218-241`) — CONNAC3, not CONNAC2:
  MCU_WM is 15, FWDL is 16, and there is no BAND1 data ring.
- Depths (Linux values, recorded in `regs.rs`): 2048 / 256 / 128 / 1536
  / 512, token 8192, TXWI 64 (`dma.rs:46`). The in-tree `DmaBuffer`
  allocator still caps a single buffer at one 4 KiB page, so rings
  program at the same 16-entry bring-up baseline as CONNAC2 until the
  multi-page allocator lands — the depths above are the target, not
  what is programmed today.
- TX-slot order is an **allocation-order convention, not a hardware
  fact** (`dma.rs:216`): BAND0 (q0) lands in slot 0, MCU_WM (q15) in
  slot 1, FWDL (q16) in slot 2 — data rings first, then MCU/FWDL
  contiguously after them, the same convention as the MT7921 map. The
  slot order is one of the open gates (§8).

## 6. EHT / MLO capability model

### EHT values: Linux's function, NARF slice 7's ownership

- There is **no NARF function `mt7925_init_eht_caps`**. That name is
  Linux's (`mt7925/main.c`), cited in the spec (:1779–1780). The local
  station capability values it computes are recorded in the spec
  (§1771+): MAC `EPCS_PRIO_ACCESS | OM_CONTROL` (0x03); PHY bytes per
  upstream for the reported streams (0xE8, 0x0D, sounding-dimension
  bits, 0xFE, 0x10, 0x61, MCS15 width bits, 0x36, 0x00); MCS/NSS tables
  `(nss << 4) | nss` per range (0x22 for two streams, 0x11 for one);
  MCS 15 advertised up to the radio's max width (20 MHz in 2.4 GHz,
  80 MHz or 160 MHz in 5 GHz); no PPE advertised.
- On the NARF tip those values are computed by slice 7
  (`mt7921::eht` / `he.rs` + `iface.rs`). `src/mt7925/mod.rs` ("Not
  here") states it plainly: this module takes EHT capability values as
  plain inputs and lays out their bytes — it never computes them. Any
  citation of a NARF `mt7925_init_eht_caps` is wrong; cite slice 7.
- Negotiated profile: EHT is opted into when the firmware PHY TLV
  reports HE (the NIC PHY TLV carries no EHT bit; upstream
  `dev->has_eht` is true for MT7925 by construction, cleared only by an
  ACPI MTCL BE-disable, `mt7925_regd_be_ctrl`, which NARF does not
  implement — that regulatory disable is a follow-up, not a
  delivered feature). The gate is the chip id, as for `vht::wide160`,
  extended from `0x7922` to `0x7922 | 0x7925`.
- Width ceiling: **160 MHz max, 320 MHz refused**. The STA record
  copies the peer MAC/PHY octets raw and the peer MCS maps; `bw80` /
  `bw160` are always copied and `bw320` stays zero. The 6 GHz branch
  appends the same record after STA_REC_HE_6G. This slice programs no
  BSS EHT record — the per-link BSS EHT info and the EHT MLD TLV
  belong to the MLO work (spec :1811).

### MLO: TLV layer landed, lifecycle in progress

- What exists on the tip (#2502, `src/mt7925/mcu.rs`):
  `MldLink` (:442, WCID index + BSS index) and `MldLinks` (:455,
  primary + `Option<secondary>`, `eml_cap: u16`), `encode_sta_rec_mld_tlv`
  (:476) and `encode_sta_rec_eht_mld_tlv` (:503), per-link TX/RX BA
  builders, per-link BSS info with MLD TLV, `build_uni_sta_update_req`
  with `mld`, and `build_uni_sta_remove_req` with `STA_REC_MLD_OFF`.
  All fixture-tested.
- Limits: **max 2 links** — primary first, at most one secondary
  (upstream `mld->link[2]`, `mcu.c:1488`; NARF has no wiphy, so there is
  no `mld_capa_and_ops` gate to mirror). The MLD TLV encodes
  `{ mac_addr[6], primary_id, secondary_id, wlan_id, link_num, rsv[3],
  link[2] }` with the primary (deflink) first; the EHT MLD TLV is
  `{ nsep = 0, mld_type = 0xff, rsv1 = 0, str_cap[3], eml_cap[3],
  rsv2[3] }` — with EMLSR the low two bytes of `eml_cap` go into
  `eml_cap[0..2]`, without it `str_cap[0] = BIT(1)`
  (`mt7925/mcu.c:2028-2062`).
- EML is caller-supplied: `MldLinks.eml_cap` is "0 when unknown" and
  the EML source belongs to slice 7 — it was not delivered with the TLV
  layer. Upstream's source, for the lane that wires it:
  `mt7925_mcu_sta_eht_mld_tlv` (`mt7925/mcu.c:2028-2062`):
  `eml_cap = (vif->cfg.eml_cap & (EMLSR_SUPP | TRANSITION_TIMEOUT)) |
  (ext_capa->eml_capabilities & (PADDING_DELAY | TRANSITION_DELAY))`.
- What does **not** exist yet: no live callers of `peer_record_uni_on`
  / `sta_remove_uni_on` were found in `station_mcu.rs` or
  `association.rs` on the tip, and `peer_record_uni_on`
  (`src/mt7921/association.rs:1078`) still sends `cap_tlvs: &[]` at
  :1111 — the UNI station update carries no capability TLVs until slice
  7 wires them (STA_REC_EHT + MLD TLVs). The MLD station lifecycle
  (add/assoc per link, secondary-link join/leave, per-link BA,
  teardown with MLD_OFF) is the parallel MLO lane's work and is
  **unmerged**; every MLO claim in this document is grounded on tip
  state only, never on that lane's unmerged work.

## 7. What is fixture-validated (and what that means)

Validated on the tip, without hardware: dual builds; the
`FIXED_MT7925` entry-for-entry golden test; firmware-blob-pair
resolution for both DIDs; the `0x25` trailer acceptance smoke; DMA
layout and ring-register golden tests; UNI/MLO TLV golden smokes
(`encode_sta_rec_mld_tlv`, `encode_sta_rec_eht_mld_tlv`,
`build_uni_sta_update_req`, `build_uni_sta_remove_req`); EHT profile
tests (80 MHz join, wide-160 negative case as a `0x7921` fixture —
upstream gates 160 MHz HE caps on `is_mt7922()`, so 7922 is a 160 MHz
part too). QEMU emulates no MediaTek Wi-Fi PCIe device, so chip-id
read, firmware download and association cannot run here; validation so
far is builds, command fixtures, native descriptor models and retained
station/reset ownership tests on both architectures — not RF acceptance.

## 8. Unverified gates (hardware-proven ≠ fixture-validated)

| Gate | What is open | What would close it |
|---|---|---|
| **Q1 — chip-id read** | `pci.rs:406` admits only `MTK_DEV_MT7961 \| MT7922 \| MT7920`; `0x7925` → `UnsupportedChip`. The gate stays closed until `MT_HW_CHIPID` is read on the real `14c3:0717` card. The module build carries the identical gate at `pci_kabi.rs:263`, so the 7925 stays unmatched in both builds. (Note: a `regs.rs:74` comment still cites the gate as `pci.rs:441`; the `matches!` is at :406 — the comment is 35 lines stale and is not fixed here.) | A boot log from Daniel's Alder Lake machine showing the `MT_HW_CHIPID` value on `57:00.0`, then admitting it at `pci.rs:406`. |
| **Q2 — blob staging** | The patch/RAM pair (§3) must be staged from Daniel's CachyOS tree before any firmware download can run. | Blobs present in the firmware tree; a FWDL run against the card. |
| **0x25 trailer byte** | The fixture convention that the trailer `chip_id` byte is `0x25` (low byte of `0x7925`, by analogy with `0x22` for MT7922) is **unverified against a real blob** — `firmware_parser_tests.rs:140`, `:149`, `:167`; spec :208–210 states the caveat. `Firmware::prepare` does not gate on it, so a wrong value would not fail loudly. | A real MT7925 RAM blob, read back and compared. |
| **DMA TX-slot order** | The slot assignment (BAND0 → 0, MCU_WM → 1, FWDL → 2) is an allocation-order convention (`dma.rs:216`), not a measured hardware fact. | A live DMA run showing rings coming up in that order. |

Until these four close, the MT7925 is implemented but unproven: the
driver will attach to the PCI ids, select the CONNAC3 table, resolve
the firmware pair and encode correct UNI/MLO bytes — and none of that
has yet been observed against the silicon.
