# narf-drivers-cyw43439 — Specification

> Status: **v0.1** (Stage 1: module + reference set + ID constants
> only; transport bring-up tracked as future stages).
>
> Clean-room driver for the **Infineon (formerly Cypress) CYW43439
> Wi-Fi 4 + Bluetooth 5 combo SoC**, the WiFi chip on the Raspberry
> Pi Pico W and a number of low-power IoT modules. **No GPL Linux
> `brcmfmac` / `bcmdhd` source consulted.**

## 1. Why this part is the bright spot

The 2026 audit of the modern WiFi flagships (iwlwifi, mt76, brcmfmac
FullMAC, ath11k, mwifiex, rtw88) concluded that all of them are
either firmware-blob driven with no public register manual, or
covered only by GPL-2.0 driver source we cannot consume.

CYW43439 is the conspicuous exception. Infineon ships:

- A complete **88-page datasheet** (Rev. 03 / v05_00) covering
  pinout, the gSPI / SDIO host-interface electrical and protocol,
  the F0/F1/F2 SDIO function model, the backplane access primitives,
  and the chip-RAM upload procedure.
- **AN232689 Wi-Fi Software User Guide**, which documents the
  conventions a host driver uses across the gSPI link.

The IOCTL / IOVAR command numbering used inside the firmware itself
is *not* in the datasheet, but two permissively-licensed reference
drivers were written from public docs and explicitly avoid GPL Linux
derivation:

- **`soypat/cyw43439`** — MIT-licensed Go reference driver.
  <https://github.com/soypat/cyw43439>
- **Embassy `cyw43`** — Apache-2.0 / MIT-licensed Rust async driver
  used in production on the Pico W.

Consuming the *interface conventions* documented in those repos is
clean-room compatible. The narf driver will lift only the public-
spec material plus the documented command numbering from the
permissive references, and will cite the specific document or
section for each entry that lands.

## 2. Public reference set

- **Infineon CYW43439 datasheet** (Rev. 03, public PDF).
  <https://www.infineon.com/part/CYW43439>
  Mirror: <https://www.mouser.com/datasheet/2/196/Infineon_CYW43439_DataSheet_v03_00_EN-3074791.pdf>
- **AN232689 — Wi-Fi Software User Guide** — Infineon application
  note, public download.
- **Bluetooth Core 5.x HCI** — the Bluetooth side of the chip rides
  standard HCI through the same combo MAC. We already have a clean-
  room HCI codec in `narf-bluetooth`.
- **soypat/cyw43439** (MIT) — IOCTL / IOVAR conventions, intended
  as a clean-room starting point.
- **Embassy `cyw43`** (Apache-2.0 / MIT) — production Rust async
  driver.

## 3. Stage plan

### Stage 1 (this commit)
- Module + spec doc presence + reference list.
- Part-number / firmware-filename constants the loader will
  eventually need (`43439A0.bin`, `43439A0.txt`, `43439A0_clm.bin`).
- SDIO function model + backplane-core-id constants from the
  datasheet (no field-by-field bitmaps yet).

### Stage 2 — Transport
- SDIO function-0 enumeration, F1 backplane window paging via
  `BACKPLANE_ADDR`, F2 WLAN bulk-data path.
- gSPI single-function variant for hosts without an SDIO controller
  (the Pico-W use case).

### Stage 3 — Firmware load
- Chip-RAM staging via the procedure documented in datasheet §6
  (load `43439A0.bin` to ARM core RAM, `43439A0.txt` NVRAM to the
  designated NVRAM offset, deassert WLAN_ARM reset).
- CLM blob upload via the IOCTL channel once IOCTL framing is up.

### Stage 4 — IOCTL / IOVAR codec
- Per-command annotation with the citing document. The command
  numbering is taken from the soypat / cyw43 permissive references;
  each number is documented with the field it controls and the
  public-doc reference (datasheet section or AN232689) that
  justifies it. Where neither document covers the field, the entry
  is marked `unverified` so a follow-up audit can revisit it.

## 4. Out of scope

- Bluetooth side — runs as standard HCI through the combo. The
  `narf-bluetooth` crate covers the HCI surface; the host driver
  here just routes the BT bytes to/from that crate.
- Higher-level 802.11 MLME — lives in `narf-wireless`.
- Firmware blob distribution — the loader path stages whatever the
  caller hands it; the blobs themselves are Infineon-distributed
  binaries the boot path supplies via the existing firmware-cap
  surface.
